Suppose in my reactive pipeline, I come across some operation such as JPA save which is non reactive and it will not return any publisher types, how can I still make my pipeline still reactive pipeline, because if I don't handle this and the pipeline will not be reactive

Basically for this scenario, all you need to do is to execute the blocking operation in a seperate thread using .subscribeOn(Schedulers.boundedElastic()) after the blocking operation or you can use .publishOn right before the blocking operation. So that beyond the point where you kept publishOn, everything will be executed in a seperate thread.(Udemy -> Reactive -> Lec 121 -> 3.32 (timestamp))

More detailed explanation :-
In a reactive pipeline, when you encounter a blocking operation such as a JPA save that does not return any reactive types (i.e., it does not return a `Mono` or `Flux`), you need to ensure that the blocking operation does not block the reactive threads and maintain the non-blocking nature of your reactive pipeline.

To handle this, you can use the `Mono.fromCallable` method combined with `subscribeOn` to execute the blocking operation on a separate scheduler. This way, you can keep your pipeline reactive while performing the blocking operation in a controlled manner.

Here's how you can do it:

1. **Wrap the blocking call in a `Mono.fromCallable`**: This allows you to convert the blocking call into a `Mono`.
2. **Use `subscribeOn` to offload the blocking call to a separate scheduler**: Typically, you would use `Schedulers.boundedElastic()` which is designed for I/O-bound work.

### Example:
Let's say you have a blocking JPA save operation that looks like this:
```java
public User save(User user) {
    // Blocking save operation
    return userRepository.save(user);
}
```

To integrate this blocking operation into a reactive pipeline, you can do the following:

```java
import reactor.core.publisher.Mono;
import reactor.core.scheduler.Schedulers;

public Mono<UserDto> updateUser(int id, Mono<UserDto> userDtoMono) {
    return userRepository.findById(id) // Assume this returns Mono<User>
            .flatMap(existingUser -> userDtoMono
                    .map(EntityDtoUtil::toEntity)
                    .doOnNext(entity -> entity.setId(id))
            )
            .flatMap(userEntity -> 
                Mono.fromCallable(() -> save(userEntity))
                    .subscribeOn(Schedulers.boundedElastic()) // Offload blocking operation
            )
            .map(EntityDtoUtil::toDto);
}
```

### Explanation:
1. **Find User**: Use `userRepository.findById(id)` to retrieve the user entity by ID, which returns a `Mono<User>`.
2. **Transform DTO to Entity**: Use `map` to transform the `UserDto` to `User` entity and set the ID.
3. **Blocking Save Operation**: Use `Mono.fromCallable(() -> save(userEntity))` to wrap the blocking `save` method.
   - `Mono.fromCallable` converts the blocking save call into a `Mono`.
   - `subscribeOn(Schedulers.boundedElastic())` offloads the blocking operation to a bounded elastic scheduler, ensuring it doesn't block the main reactive pipeline.
4. **Transform Entity back to DTO**: Use `map` to transform the saved `User` entity back to `UserDto`.

By using `Mono.fromCallable` and `subscribeOn`, you ensure that the blocking JPA save operation is handled in a non-blocking manner, keeping your reactive pipeline reactive and efficient.
